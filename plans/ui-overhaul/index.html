The goal is an elegant, useful daily application with a convincing Homeric world: Greek coastal light, Spartan discipline, Roman clarity, original artwork, and a journal that feels like writing a scroll. Professional quality comes from readable content, clear actions, reliable feedback, and consistent spacing on every route.

Confirmed decisions

  • Tone: disciplined and challenging, without punishment.
  • Device priorities: phone for daily check-ins; desktop for planning and journaling. All existing workflows must remain usable on mobile.
  • Journal: headings, bold/italic, bullet and numbered lists, checklists, quotations, links, undo/redo, autosave, and focus mode.
  • Scope: UI and frontend interaction overhaul. Preserve existing data, routes, authentication, task schedules, quest rules, and ownership.
  • Visual commitment: Greek/Roman/Spartan Odyssey/Iliad inspiration, custom-generated imagery, and a modern elegant finish.
  • Still open: final light/dark emphasis, degree of figurative/mythic art, and swipe confirmation behavior. Recommendations below are proposals, not user approvals.

The proposed visual world

Spartan Standard is the lead proposal. Rich oxblood gives navigation a clear identity; smoked Aegean teal gives working areas depth; ivory text and controlled bronze actions make the next step visible. Artwork depicts journeys, coastlines, crafted objects, and human effort. A few precise historical details carry the world through an otherwise familiar professional application.

The defining moment is the daily commitment card: one readable task, one evocative piece of art, a visible Done/Skip pair, and a deliberate horizontal gesture. The scroll editor is the second expression of that same material world.

Aegean Passage is the lighter alternative shown in the fourth generated preview: cool limestone surfaces, dark ink, an indigo shell and actions, and sunlit original artwork. It is equally functional, with a stronger daylight feel.

The historical source is a coherent artistic interpretation. Homeric Greece leads; Spartan cloth, bronze, and Roman inscription proportions support it. This is not a claim of archaeological reconstruction. Control names remain Check-In, Tasks, Quests, Journal, Insights, and Settings.

What the concept images settle and what they do not

The four generated images test atmosphere, hierarchy, imagery and layout. They are illustrative proposals with sample content, not implemented screenshots, proof of accessibility, or approval of a new logo. Text and controls will be real HTML in the application.

Known concept-only details to correct in implementation: the dark Tasks comp substitutes Wisdom/Community/Purpose for three dimensions; the actual names remain Wealth/Alliance/Legacy. Its row checkboxes are illustrative and will not introduce an unplanned task-completion workflow. Any generated laurel mark is a placeholder until a logo decision is made. Sample dates and activity marks are not user data. The lighter comp also uses some display type in controls; final controls use the readable UI family consistently. Final texture will be quieter than these art-direction images, especially behind text.

Proposed foundation

  • Expression: moderate and recognizable in working screens, strongest on entry, check-in and the journal. Design variance 6/10, motion intensity 4/10, visual density 5/10 for planning and 3/10 for focused writing/check-in.
  • Typography: a self-hosted inscription-inspired display face for Odyssey and selected headings; a readable humanist sans for navigation, forms and data; an optional book serif for journal prose. Candidate roles: Marcellus, Source Sans 3, and Literata. Final faces are chosen against the approved comps and licensing.
  • Scale: 16px base body; 14-16px metadata; 16px minimum editable mobile controls; 18-20px journal text with 1.65-1.8 line-height. Avoid tiny tracked capitals.
  • Spacing: one 4/8px rhythm, 16-24px group spacing, 32-40px between major regions. Desktop navigation uses consistent approximately 48px rows with a small fixed gap; it never distributes links over the full height.
  • Shape: restrained corners for working surfaces and controls. More generous corners belong to the gesture card; pills are reserved for compact tags.
  • Color: semantic tokens for surface, text, action, border, focus and each state. Six dimensions have readable names and distinct icon/color pairing. Color never carries a state alone. Bronze buttons receive dark labels.
  • Themes: design light and dark variants of the same system, with a system/manual preference in Settings. The preferred emphasis remains a review choice. The journal may use a light paper document inside the dark application surround.
  • Icons: one maintained family, proposed Phosphor, with one weight and clear accessible names. Generated illustrations do not replace control icons.
  • Data honesty: display actual API values. Remove the fixed Life Balance shape; show an explicit unavailable-data explanation until real dimension scores exist.

Navigation and responsive structure

Desktop and tablet

Reuse the current router and routes. A steady 224-240px sidebar holds the existing destinations; account and Settings remain at the bottom. Page headers align title, short context and one primary action. Long lists use the full useful work area. The shell uses bounded line lengths, not arbitrary large empty areas.

Medium widths use a compact rail or clearly labeled menu before the sidebar crowds the work. Do not switch a large tablet to tiny phone navigation merely because it crosses the current 1120px breakpoint.

Phone

Keep five core destinations in a persistent bottom bar, with an always-visible Account button opening Settings, Help and Logout. Show labels at readable sizes, announce the active destination, and respect safe-area insets. Check-in can enter focus mode, with a clearly labeled exit; focus mode is explicit, never a trap.

Allow normal pinch zoom. Keep the existing device-width viewport policy; do not add maximum-scale or user-scalable restrictions. Fix intrinsic widths and layout overflow, use at least 16px mobile input text, avoid automatic focus on route entry, and handle virtual-keyboard/safe-area geometry.

Screen-by-screen overhaul

Sign in and registration

Original artwork introduces the world in a split desktop composition. The form remains compact with persistent labels, password reveal, correct autocomplete, visible validation and recovery. Mobile reduces the artwork and leads with the form; it must not make users scroll past a cinematic introduction to sign in.

Onboarding

Introduce the six existing dimensions through six consistent original vignettes and concise explanations. The starter task remains the main action. Do not turn setup into a mandatory animation or invent new scoring. Cross-browser onboarding persistence is a separate product issue because the current flag is browser-local.

Daily check-in

One task at a time with date, clear progress, category, schedule and primary actions. Artwork makes each commitment feel situated without competing with its title. Done and Skip remain visible even when swipe is available. Optional value entry is progressively disclosed. Completed, no-tasks-due, loading and failed-load screens have distinct wording and next actions.

A truthful completion summary offers Journal or Insights. Avoid saying every task was done when some were skipped, and distinguish no tasks due from having completed existing tasks.

Tasks

A compact useful library with labeled search, dimension/type/status filters and a primary New task action. Desktop rows expose title, schedule, status, edit and activity. Phone rows stack the same information and put secondary actions in an accessible menu. Filters wrap or open a sheet; they cannot widen the document.

Expanded history shows a readable legend, date range and accessible summary. Avoid hundreds of independent tab stops in the heatmap. Create/edit use the same labeled fields, schedule controls and validation; long content scrolls while actions remain reachable. Confirm deletion and describe the affected history.

Quests

Desktop master/detail: readable goal list on the left, selected quest and milestones on the right. On phone, open a focused detail state with Back to Quests, preserving list/filter position. Selection is a real link or button. Keep progress and milestone behavior tied to current APIs.

Use bespoke landscape/object art in headers or genuinely empty states. Milestones use proper checkboxes, inline pending feedback and understandable completion. Activity history remains reachable without competing with the next action.

Journal library and reader

Keep date grouping, search and dimension filters. A clear New entry action leads. Previews show readable text, title, date and meaningful tags; they do not display stored formatting syntax. Empty library, empty search, loading and failed load are separate states. The reader reuses the editor's document typography and document parser, with clear Edit, Back and a protected delete action.

Scroll editor

The document is a continuous writing surface with subtle papyrus material, generous margins and strong ink contrast. A small rolled-edge or seal detail may frame the document, but writing uses normal scrolling and selection.

A sticky toolbar groups text style, inline emphasis, lists/checklists, quote/link, and undo/redo. Selected formatting has semantic pressed states and visible focus. Focus mode hides secondary metadata; it never hides save state or the exit.

Title, tags and dimensions remain editable, with metadata secondary to writing. Desktop line length stays around 65-75 characters. On mobile, use a compact keyboard-aware toolbar and a More menu for lower-frequency actions. Long typing, text selection and the virtual keyboard must work without fighting the bottom bar.

Save states are explicit: Unsaved changes, Saving, Saved, Save failed with Retry. A failed save keeps the editor open. Serialize writes so a slower old response cannot overwrite a newer draft or falsely claim the newest edit is saved. Failed saves keep the editor open. In-app navigation offers Save, Discard and Stay; browser-back navigation needs the same guard where the router supports it. Hard reloads, tab termination and crashes cannot guarantee draft recovery without explicitly approved durable local draft storage.

Insights

Lead with the selected date range and the metrics actually returned by the API: task completions/skips, current check-in streak, quest updates and journal count. There is no separate check-in completion-count field in the current overview API. Add accessible text equivalents for all charts. Remove hard-coded balance values. Use totals language when a count is not actually filtered to active items.

The data should feel authored and readable, with warm visual detail around it, but never imply scores, trends or per-dimension analytics the API does not supply.

Settings and Help

Provide reachable account/session controls plus appearance and motion preferences. Existing account fields are informational unless supported editing is deliberately added later. Help preserves the useful task/quest templates and six-dimension explanations, with accessible disclosures and readable guidance.

Swipe and motion specification

Gesture contract

Proposed mapping: swipe right for Done, left for Skip. Before release, reveal both the direction and its text action. Commit only after clear horizontal intent and a substantial distance threshold; short or cancelled drags return to rest. The initial tuning target is roughly a quarter of card width, verified on phones.

Preserve vertical scrolling and operating-system edge gestures. Do not start a drag from an input, button or text selection. Prevent duplicate submissions; on failure restore the card with an inline Retry. Announce saved outcomes and the next task through a polite live region.

Do not promise post-save Undo in this UI-only pass. The response API has no clear-response operation, and completing a one-time task archives it. A real Undo needs a separate contract decision. The review form offers a safer reveal-then-tap variant if immediate release-to-save feels too risky.

Motion language

  • Task response: a weighted lateral exit and next-card settle, approximately 180-240ms, communicating that an answer was recorded.
  • Panel/menu opening: restrained directional movement, approximately 160-220ms, tied to where the control opened.
  • Quest milestone: a brief state change and progress update, not a fireworks reward.
  • Journal entry: a quiet document reveal, once; while writing, keep the surface still.
  • Buttons: short press feedback. Navigation selection remains stable and readable.
  • Reduced motion: remove travel, tilt and unrolling; retain clear state and save feedback through immediate changes or a brief fade.

Use transform/opacity for ordinary UI transitions. Avoid infinite shimmer, glowing nav labels, bouncing controls, scroll hijacking and decorative particles. The era comes from material, imagery and deliberate weight, not animation delays.

Accessibility and affordances

Target WCAG 2.2 AA. This is an implementation requirement, not a claim that the generated images pass. Use a 44-48px touch-target design goal, clear persistent labels, visible focus, meaningful button names and sufficient text/control contrast. Verify body and placeholder text at least 4.5:1 and non-text control boundaries at least 3:1 where required, on the actual rendered surfaces.

Support keyboard navigation throughout; expose filter selection semantically. Dialogs manage initial focus, trapping, Escape, background inertness, scroll restoration and focus return. Prefer accessible maintained primitives over rebuilding modal behavior repeatedly. Destructive confirmation initially focuses the safe action.

Support 200% zoom and reflow at narrow widths, long titles, large text, screen-reader status announcements and reduced motion. Use clear words plus icons/colors for status. Replace nested link/button markup with one appropriate interactive element.

Custom image production plan

All four preview images were produced with the built-in imagegen tool. Exact prompts are saved under prompts/; original PNGs carry embedded provenance and optimized WebP previews carry adjacent provenance sidecars. These previews are concept art. Production art is regenerated separately at its placement's dimensions; UI screenshots are not sliced up to create artwork.

Proposed original asset family

  • Entry panorama: an Aegean harbor, a coastal path and a small distant traveler; landscape and portrait compositions, with usable negative space.
  • Check-in art: calm paths and purposeful movement; category-specific variants selected from a small set rather than fetching a new image per interaction.
  • Quest art: ascent, distant sanctuary, navigation and crafted objects, supporting long-term effort without implying a reward system.
  • Journal material: clean, subtle papyrus fiber and optional edge details, tested at reading scale. The texture never reduces legibility.
  • Six vignettes: Vitality, Psyche, Prowess, Wealth, Alliance and Legacy in one visual medium and lighting family. Suggested objects include an olive branch, still water/owl, a stylus/worked tool, an amphora/granary, a joined cord, and a carved enduring mark. These are proposals pending the imagery preference.
  • Empty/completion scenes: small, purposeful illustrations with clear text and actions, rather than empty full-screen darkness.

Keep imagery original; do not copy game screenshots or actor likenesses. Generated art carries no UI text. Final assets receive informative alt text when meaningful, and empty alt text when purely decorative. Use responsive crops, reserved dimensions and WebP/AVIF where supported. Initial budgets: under roughly 250KB for a desktop banner and 150KB for mobile, subject to measured visual quality. Avoid loading all scene variants before the first action.

Implementation approach and boundaries

Retain React/TypeScript, Vite, Tailwind v4, React Router and the existing API client. Do not migrate frameworks. Build the shared visual/interaction foundation once, then apply it to every route.

Proposed additions are limited to a maintained headless rich-text editor, accessible overlay/menu primitives, one icon family, self-hosted fonts, and generated art. Tiptap is the recommended editor candidate; Radix Primitives can supply overlay behavior while our styles supply the Odyssey identity. No dependencies are installed during planning.

Tiptap's official Markdown bridge currently carries a beta warning. That makes a format round-trip spike a prerequisite rather than a promise of instant fidelity. The official Radix Dialog supports focus trapping and Escape behavior; wrappers still need appropriate labels, layout and end-to-end verification. Sources: Tiptap Markdown, Radix Dialog.

Rich-text storage decision

The current API and database store content: string; list/read screens render it as plain text and server search uses substring matching on the string. A toolbar alone cannot safely implement rich text.

Proposed UI-only approach: an explicitly versioned Markdown document inside that existing string, parsed by one shared frontend adapter. Unmarked existing entries remain literal plain text, preserving old asterisks, angle brackets and line breaks. Only a deliberate save converts an edited legacy entry to the new format. The parser strips the version marker before handing content to editor libraries.

The adapter provides document load, save, safe read rendering and plain-text preview/word count. Support only the agreed formatting subset. Disable raw HTML and unsafe link schemes, and test pasted content. Guard unknown format versions with a readable fallback rather than silently overwriting them.

This avoids a database migration but has a trade-off: existing server search still searches stored Markdown, so an exact phrase split by formatting may not match. Full formatting-insensitive search or a first-class format column is a separately identified backend improvement. If those are required now, expand scope explicitly before implementation.

Send explicit null/empty values where the current PATCH contract supports clearing title/tags/categories; do not let trimPayload erase the user's clear action. The API accepts nullable title and list metadata, and the update handler uses exclude_unset=True, so clearing can be handled without a new endpoint. Do not create/save an empty document merely because the user opened the editor.

Other boundaries

Theme preferences can remain browser-local in this pass; cross-device settings need persistence work outside this UI plan. Keep autosave failure protection within the editor; durable browser storage of sensitive drafts is an explicit privacy choice, not an automatic addition. No file uploads, image insertion, tables, collaboration, AI mentor, XP, scoring, notifications or new backend services are included. Preserve the existing form field order unless the review approves a change.

Acceptance checklist

  • All routes, Settings, Help and Logout are reachable by keyboard and phone.
  • No document-level horizontal overflow at 320, 390, 768, 1024 and 1440px; verify reflow and 200% zoom.
  • Reproduce and verify the reported zoom issue on the affected real Safari/browser/device; do not disable pinch zoom.
  • Measure actual text, input, button, selected and focus-state contrast in both themes.
  • Initial focus, trap, Escape, background inertness, scroll restore and focus return work.
  • Gesture threshold/cancel, vertical scrolling, duplicate prevention, failure restoration and button/keyboard alternatives work.
  • Every agreed formatting feature survives save/reload/read/edit; legacy entries remain readable.
  • A failed save cannot close the editor or report unsaved content as saved.
  • Clearing title, tags and dimensions persists correctly.
  • Libraries distinguish genuine-empty, filtered-empty, loading, error/retry, pending and success.
  • No fabricated scores or charts; date navigation works around midnight in Asia/Kolkata.
  • Reduced-motion mode preserves every task and outcome without spatial choreography.
  • Reserve asset dimensions; lazy-load editor and noncritical art; measure LCP, INP and layout shift.
  • Frontend build/lint, focused UI logic tests and existing backend tests pass.
